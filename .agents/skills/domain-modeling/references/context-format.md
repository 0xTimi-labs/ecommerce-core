# 上下文格式

## 单上下文格式

```md
# {上下文名称}

{一两句话说明该上下文是什么、为什么存在}

## 术语

**订单**:
客户下单后产生的交易记录
等价: Order
避免: 采购单, 交易, PurchaseOrder

**发票**:
客户付款的凭证
等价: Invoice
避免: 账单, 付款单, Bill

**客户**:
在系统内发起订单交易的业务主体
等价: Customer
避免: 消费者, 账户, Client

**SKU**:
库存商品的唯一编码
避免: 库存编码, 货号
```

## 规则

- **有主见**：同一概念有多个词时，选定共识最强的标准词，其余列入“避免”，“等价”记录代码或文档中的规范名称
- **避免是换词指引**：“避免”约束指代该概念时的用词，不是全局禁用——易混词（如交易之于订单）在其他上下文可以是合法术语
- **定义紧凑**：最多一两句话，定义它**是什么**，而不是它做什么
- **只收本上下文特有的术语**：通用编程概念（超时、错误类型、工具模式）不属于这里，即使项目大量使用
- **自然成簇时分组**：术语形成自然聚类时用子标题分组；全部属于同一领域时平铺即可

## 多上下文格式

```md
# 上下文地图

## 上下文

- [订单](./src/order/context.md) — 接收并跟踪客户订单
- [账务](./src/billing/context.md) — 生成发票并处理付款
- [履约](./src/fulfillment/context.md) — 管理仓库拣货与发货

## 关系模式

- **订单 [U, OHS, PL] → 履约 [D, ACL]**
    - **事件**：发布 `OrderPlaced`，订阅生成 `PickTask`
    - **查询**：REST API 获取订单状态
    - **命令**：缺货时 REST API 执行 `SuspendOrder`
- **履约 [U, PL] → 账务 [D, ACL]**
    - **事件**：发布 `ShipmentDispatched`，订阅生成发票
- **订单 ↔ 账务 [SK]**
    - **共享**：`CustomerId` 与 `Money` 类型
```

## 标记说明

- **U**: 上游 `Upstream`
- **D**: 下游 `Downstream`
- **OHS**: 开放服务 `Open Host Service`
- **PL**: 发布者语言 `Published Language`
- **ACL**: 防腐层 `Anticorruption Layer`
- **SK**: 共享内核 `Shared Kernel`

## 单→多切换

单一 `context.md` 假设整个项目一种语言，以下信号出现时拆分为多上下文：

- **语言分歧**：同一概念在两处有不同定义或名称——如 Customer 在 ordering 是"下单主体"、在 billing 是"付款主体"，单一术语表无法表达一词两义
- **术语成簇**：术语明显分属两簇、各自只属于一个模块，共享概念寥寥

代码出现两个独立模块仅作辅助确认：语言统一的两个模块共用一个 `context.md` 即可，不必拆

拆分后根目录只保留 `context-map.md`：各上下文在各自目录新建 `context.md`；原术语按各上下文的视角重新归属、重写定义；已有 ADR 的处置见 [adr-format.md](./adr-format.md)
