# ADR 格式

ADR 就近存放：全局决策放根 `docs/adr/`，上下文专属决策放各上下文目录内的 `docs/adr/`（如 `src/ordering/docs/adr/`）。决策敲定后即刻写入，不要等批量处理。顺序编号：`0001-slug.md`、`0002-slug.md`

上下文拆分时，已有 ADR 按内容归属迁入对应上下文的 `docs/adr/`，跨上下文的全局决策留在根 `docs/adr/`；迁入后保留原编号，各目录内续编

## 模板

```md
# {决策的简短标题}

{1-3 句话：背景是什么、我们决定做什么、为什么}
```

## 可选小节

只有真正有价值时才包含，绝大多数 ADR 不需要：

- **备选方案**，仅当被否掉的备选方案值得记住时
- **影响**，仅当有非显而易见的后果需要说明时

## 哪些值得记录

- **架构形状决策**：如采用 Monorepo、事件驱动写模型等
- **上下文间的集成模式**：如 Ordering 和 Billing 通过领域事件通信，而非同步 HTTP
- **带锁定效应的技术选型**：如数据库、消息总线、认证服务商、部署目标，仅限替换成本极高的那些，而非所有库
- **边界与范围决策**：如客户数据归 Customer 上下文所有，其他上下文只按 ID 引用。明确的不做什么与做什么一样值得记录
- **对显而易见路径的有意偏离**：如手写 SQL 而非 ORM，任何合理读者会假设相反做法的东西都算，能阻止后来的工程师"修好"一个有意为之的设计
- **代码中不可见的约束**：如合规要求下不能用 AWS；合作方 API 合同要求响应时间低于 200ms
- **被否备选方案**：如考虑过 GraphQL 而选了 REST 且理由微妙，记录下来，否则半年后又会有人提议 GraphQL

> 如果已记录的决策失效，需即刻删除并重新编号
